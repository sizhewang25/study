## B. Description errors (text vs implementation or data)

- **B1 (methodology l.24):** Octant "keeps the face within a desired weight threshold". Every Octant combo sets `highest_weight_only: true`, so it keeps the single highest-weight face and ignores `weight_threshold`.
- **B2 (methodology l.13):** "the greedy filter of darwich:imc23 removes TGs". The pro sanitizer (`scripts/processing/source/sanitize_target_ground_truth_soi.py`) uses two stages:
  - it drops a TG when more than 5% of its pairs violate SOI;
  - for the TGs it keeps, it drops only the violating pairs.

  So the mesh is not full: 98, 79 and 71 TGs (AS-A/B/C) lack some VPs, and one AS-B TG has only 26.
- **B3 (methodology l.13):** "final window one week". The CSVs are `20260728-20260802`, which is 6 days.
- **B4 (testbed, §3/§6):** the paper says "32-GB VM" and the intro says "32 cores". No run.json records the host. This workstation has 16 cores and 15 GB. Confirm where the benchmark ran.

## E. Convention / confidentiality risks

- **E1, D can be recovered (§4).** The thresholds 3.4, 22.8, 228 and 4.6 (×10⁻³) are exactly 15, 100, 1000 and 20 km divided by D = 4387.257. Together with "1 ms ↔ 100 km", a reader can back out D (1000/0.228 ≈ 4386 km). Fix A1, A3 and A5 with the artifact values, or use percentiles, which also removes the pattern.
- **E2, absolute site counts (§5 l.27).** "three sites … two sites in AS-A … one site in AS-C … two sites in AS-B". Use "a few sites".
- **E3, real location (§5 l.96 rednote).** "the Seattle site" names a real site.
- **E4, counts can be backed out (methodology l.11).** "20 IPs per site (10 v4 + 10 v6)", together with "folds = number of sites", lets a reader back out the site count. This is borderline.
- **E5, caption wording (cost box).** It says "OCT-H with the only EST phase change". The PNG legend says "GEO CTR", while the prose uses EST.
- **E6, RIPE figure (§8).**
  - The caption is the placeholder "CDF", and the figure has no `\label`.
  - The axis is absolute km rather than d/D. That is acceptable for public RIPE data, but inconsistent with the rest of the paper.
- **E7, memory understated (§6).** "≈1.2 GB for 32 workers" counts the per-TG heap only. Each worker's RSS is about 270–300 MiB (`run_peak_rss_bytes`), so the real figure is about 9 GiB. That is still under 32 GB, but about 8× higher.
- **E8, wording (§5 l.144).** "TGs that only SPO classifies correctly (11%)" means SPO-but-not-OCT-H. Line 135 uses "only" for single-method (8%). Reword as the caption does.
